## c4_acknowledge_units

Say a person has failed units in hand so the farm stops asking: acknowledge (you take them), assign (to assignee), or accept (the failure stands; the units count as done, so nothing waits on them). Recorded with who and when, and signed in the book. A requeue clears it. Units is a set like "14" or "0-9,14"; only failed units are taken.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "assignee": {
      "description": "with assign, who has them",
      "type": "string"
    },
    "kind": {
      "description": "acknowledge (default), assign or accept",
      "type": "string"
    },
    "name": {
      "description": "the job's name",
      "type": "string"
    },
    "namespace": {
      "description": "the job's namespace",
      "type": "string"
    },
    "note": {
      "description": "why, for the book",
      "type": "string"
    },
    "units": {
      "description": "a unit set, for example 14 or 0-9,14",
      "type": "string"
    }
  },
  "required": [
    "namespace",
    "name",
    "units"
  ],
  "type": "object"
}
```

## c4_deadline_options

What tighter deadlines would take for a job, without changing anything. With no times given, it offers the choices itself: the project's upcoming review sessions (dailies and the like) before the job's deadline, and the earliest time it makes at 80% without making another job late. For each time: the finish band and which percentile is on time, the smallest boost that makes it, the burst capacity and its cost (and whether it needs approval), how many other jobs it would make late (named only in your projects), and, when nothing makes it, the earliest the job can finish. Suggested deadlines are generous; tightening one is your choice, made with c4_set_deadline.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "at": {
      "description": "candidate deadlines, up to 8 RFC 3339 times (for example 2026-10-23T18:00:00-07:00); none: the tighter choices the farm offers",
      "items": {
        "type": "string"
      },
      "type": [
        "null",
        "array"
      ]
    },
    "name": {
      "description": "the job's name",
      "type": "string"
    },
    "namespace": {
      "description": "the job's namespace",
      "type": "string"
    }
  },
  "required": [
    "namespace",
    "name",
    "at"
  ],
  "type": "object"
}
```

## c4_decide

Decide a job's wait for a person (a ruling, an approval, an outside party's answer): do is approve, one of the wait's choices, or fail. A wait that asks for a reply (reply in c4_job_detail's waits) takes one with the decision, reply_text or reply_view, which the units it holds up read. Or decide a unit a review escalated: accept (it stands), rework (it runs again) or fail. The job's waits, and whether each holds up work, are in c4_job_detail. Signed and recorded in the book.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "do": {
      "description": "approve, one of the wait's choices, or fail; for an escalated unit accept, rework or fail",
      "type": "string"
    },
    "name": {
      "description": "the job's name",
      "type": "string"
    },
    "namespace": {
      "description": "the job's namespace",
      "type": "string"
    },
    "note": {
      "description": "why, for the book",
      "type": "string"
    },
    "reply_text": {
      "description": "the decision's content, for a wait that asks for a reply: stored as reply.md, which the units it holds up read",
      "type": "string"
    },
    "reply_view": {
      "description": "the decision's content as a view already in the project's store (its C4 ID), instead of reply_text",
      "type": "string"
    },
    "unit": {
      "description": "the waiting unit's name or index",
      "type": "string"
    }
  },
  "required": [
    "namespace",
    "name",
    "unit",
    "do"
  ],
  "type": "object"
}
```

## c4_grant

Let a production tracker's sync (a Tracker: GitHub, Flow, ...) submit work for the person you act for, so jobs it makes from their issues or tasks are theirs and what is theirs (a lease of their own sign-in) serves them. Only when that person asks: the grant is theirs, signed and recorded in the book. Optionally limit it to pools and job classes; it ends at until (30d by default, at most 90d). Granting again renews it.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "classes": {
      "description": "only jobs of these classes",
      "items": {
        "type": "string"
      },
      "type": [
        "null",
        "array"
      ]
    },
    "namespace": {
      "description": "or the namespace the tracker is in",
      "type": "string"
    },
    "pools": {
      "description": "only jobs in these pools",
      "items": {
        "type": "string"
      },
      "type": [
        "null",
        "array"
      ]
    },
    "project": {
      "description": "the project the tracker is in (one you can see may be left out)",
      "type": "string"
    },
    "tracker": {
      "description": "the tracker's name",
      "type": "string"
    },
    "until": {
      "description": "when it ends: an RFC 3339 time or a span like 30d (default 30d, at most 90d)",
      "type": "string"
    }
  },
  "required": [
    "tracker"
  ],
  "type": "object"
}
```
