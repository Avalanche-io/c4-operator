## c4_acknowledge_units

Say a person has failed units in hand so the farm stops asking: acknowledge (you take them), assign (to assignee), or accept (the failure stands; the units count as done, so nothing waits on them). Recorded with who and when, and signed in the book. A requeue clears it. Units is a set like "14" or "0-9,14"; only failed units are taken.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "assignee": {
      "description": "with assign, who has them",
      "type": "string"
    },
    "kind": {
      "description": "acknowledge (default), assign or accept",
      "type": "string"
    },
    "name": {
      "description": "the job's name",
      "type": "string"
    },
    "namespace": {
      "description": "the job's namespace",
      "type": "string"
    },
    "note": {
      "description": "why, for the book",
      "type": "string"
    },
    "units": {
      "description": "a unit set, for example 14 or 0-9,14",
      "type": "string"
    }
  },
  "required": [
    "namespace",
    "name",
    "units"
  ],
  "type": "object"
}
```

## c4_agent

Start a worker, or several at once (workers), as you would start subagents: the farm runs each as a fresh Claude Code session from its brief alone (it sees nothing of this conversation), on a branch of its own from your HEAD (base), in your own job, which the first call makes and later calls add to. It waits up to 3 minutes and returns each worker's result: its summary in its own words, its branch, how it ended, or the question it stopped on (answer with c4_supply). Workers still running come back with their units: wait for them with c4 farm wait as a background command. background answers at once. Commit what the workers need first: they start from a commit. Only a lead, a person's own session, starts workers; a worker cannot.

## c4_deadline_options

What tighter deadlines would take for a job, without changing anything. With no times given, it offers the choices itself: the project's upcoming review sessions (dailies and the like) before the job's deadline, and the earliest time it makes at 80% without making another job late. For each time: the finish band and which percentile is on time, the smallest boost that makes it, the burst capacity and its cost (and whether it needs approval), how many other jobs it would make late (named only in your projects), and, when nothing makes it, the earliest the job can finish. Suggested deadlines are generous; tightening one is your choice, made with c4_set_deadline.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "at": {
      "description": "candidate deadlines, up to 8 RFC 3339 times (for example 2026-10-23T18:00:00-07:00); none: the tighter choices the farm offers",
      "items": {
        "type": "string"
      },
      "type": [
        "null",
        "array"
      ]
    },
    "name": {
      "description": "the job's name",
      "type": "string"
    },
    "namespace": {
      "description": "the job's namespace",
      "type": "string"
    }
  },
  "required": [
    "namespace",
    "name",
    "at"
  ],
  "type": "object"
}
```

## c4_decide

Decide a job's wait for a person (a ruling, an approval, an outside party's answer): do is approve, one of the wait's choices, or fail. A wait that asks for a reply (reply in c4_get_job's waits) takes one with the decision, reply_text or reply_view, which the units it holds up read. Or decide a unit a review escalated: accept (it stands), rework (it runs again) or fail. The job's waits, and whether each holds up work, are in c4_get_job. Signed and recorded in the book.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "do": {
      "description": "approve, one of the wait's choices, or fail; for an escalated unit accept, rework or fail",
      "type": "string"
    },
    "name": {
      "description": "the job's name",
      "type": "string"
    },
    "namespace": {
      "description": "the job's namespace",
      "type": "string"
    },
    "note": {
      "description": "why, for the book",
      "type": "string"
    },
    "reply_text": {
      "description": "the decision's content, for a wait that asks for a reply: stored as reply.md, which the units it holds up read",
      "type": "string"
    },
    "reply_view": {
      "description": "the decision's content as a view already in the project's store (its C4 ID), instead of reply_text",
      "type": "string"
    },
    "unit": {
      "description": "the waiting unit's name or index",
      "type": "string"
    }
  },
  "required": [
    "namespace",
    "name",
    "unit",
    "do"
  ],
  "type": "object"
}
```

Every signed record between a file a job wrote and where its inputs came from, each verified with its signer: the task record (signed by the node that ran the unit), each input's resolution (the controller), the input's origin (an import or ingest signed by a workload, or the upstream job's record signed by the queue, with its scheduling decisions, the HUD and MCP actions on it, its own task records and inputs), and the job's own record. Reports verified (every record checks out and was signed by whom the farm's policy wants), complete (no step lacks a record), the distinct signers, and any gaps.

Input:

```json
{
  "additionalProperties": false,
  "properties": {
    "name": {
      "description": "the job's name",
      "type": "string"
    },
    "namespace": {
      "description": "the job's namespace",
      "type": "string"
    },
    "path": {
      "description": "a file the job wrote, relative to its output view, for example renders/sh010/sh010.1039.exr",
      "type": "string"
    },
    "unit": {
      "description": "or a unit index, for the unit's own record",
      "type": [
        "null",
        "integer"
      ]
    }
  },
  "required": [
    "namespace",
    "name"
  ],
  "type": "object"
}
```
